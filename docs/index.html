apache metamodel · the audit and the fork
An unofficial fork of a retired project

Apache MetaModel was retired
in June 2021. These fixes will never be released.

The ASF does not release retired projects, so the last upstream commit is the last thing that will ever be published under org.apache.metamodel — including its security holes. This is the record of a full audit of the library: what was found, what was fixed, what was proved not to be a defect, and what is still not released.

Chapter 01

The headline finding

JDBC-10 — an S1 SQL injection in the JDBC layer, and the reason this fork exists. Query.clone() cloned the select-clause items with the cloned query, so their SelectItems were re-bound to the cloned FromItems. But it cloned the where-, group-by-, having- and order-by items without it, so their select items kept a detached copy of the from item.

The JDBC module quotes and escapes the alias of a from item after cloning — so the FROM clause rendered the escaped alias while the WHERE clause rendered the original, unquoted and unescaped.

S1 — and it was not the only one

The same class of defect appeared four times: the from-item alias (JDBC-10), the primary-key column list and the schema name (JDBC-02), the schema name in every dialect except Postgres (FM-04), and a second injection path that only surfaced by testing the first fix (FM-05). 62 of the 64 defects were fixed; 0 remain open.

Chapter 02

What was audited

Thirty modules, and a defect class list rather than a hunch. The audit was scoped by docs/AUDIT-BRIEF.md, which named the classes to hunt rather than the files to read — because a brief that lists files produces a checklist, and a checklist is what an audit must not be.

Classes hunted

  • XML External Entity processing (CWE-611)
  • SQL injection through identifier quoting (CWE-89)
  • Unsafe deserialization (CWE-502)
  • Credential handling in logs and errors
  • Correctness of the query and model layer
  • The build itself, the toolchain, and the dependencies

The surface

  • 30 modules — JDBC, XML, Excel, CSV, Elasticsearch, MongoDB, Cassandra, CouchDB, Neo4j, DynamoDB, Salesforce, SugarCRM, POJO, OpenOffice, Spring
  • 523 main source files, 198 test files
  • Java 8 bytecode — the library's floor, unchanged by the fork
  • Live datastores for the adapters, not mocks

SC-01 S1 build core
Every legacy MetaModel stream failed to deserialize on JDK 9+.

Where: core/.../util/LegacyDeserializationObjectInputStream.java

Every legacy MetaModel stream failed to deserialize on JDK 9+. The class detected "this stream described an enum" by reflecting into java.io.ObjectStreamClass's private initialized field and its isEnum() member. Since Java 9 (JEP 403) setAccessible on java.io internals throws InaccessibleObjectException; the exception was swallowed by catch (Exception e), the helper silently returned false, the legacy enum descriptor was bound to the modern OperatorType interface, and the JDK rejected it with InvalidClassException: cannot bind enum descriptor to a non-enum class. The project's own CI only ever ran JDK 8/9/11, so this was never seen.

Resolution: Fixed — replaced the reflection with the public-API signal the JDK itself guarantees for enum descriptors (getSerialVersionUID() == 0 && getFields().length == 0), which is what ObjectStreamClass.readNonProxy enforces. Mutation-proved: with the detection disabled the original error returns exactly.

mutation-proved — the new test fails against the pre-fix code

FM-04 S1 security jdbc
The schema name broke out of the identifier in every dialect except PostgreSQL.

Where: jdbc/.../dialects/DefaultQueryRewriter.java (all dialects)

The schema name broke out of the identifier in every dialect except PostgreSQL. Core renders the schema name raw (core/query/FromItem.java:227), and only PostgresqlQueryRewriter overrode rewriteFromItem; the other eleven dialects inherited the base, which emitted the schema unquoted and unescaped. A schema named x"y produced FROM x"y."t" — the attacker's own quote closes the identifier. PostgreSQL quoted the schema but did not double an embedded quote, so "x"y"."t" still broke out.

Resolution: Fixed — escapeIdentifier (doubles the quote character) and needsIdentifierQuoting (quote only when protection is actually needed, so ordinary schema names render byte-identically to before) are applied to the table reference and both sides of a join. PostgreSQL keeps its always-quoted form and now doubles embedded quotes. Proved: disabling the guard makes the new test fail.
FM-05 S1 security jdbc
A second injection path, found only by testing the fix.

Where: jdbc/.../dialects/DefaultQueryRewriter.java (rewriteSelectItem / rewriteOrderByItem / rewriteGroupByItem / rewriteFilterItem)

Resolution: Fixed — the column-path qualifiers are protected too. Proved (the SQL Server dialect failed the new test after only the FROM clause had been fixed, which is how the path was found).

JDBC-11 S2 correctness jdbc
A concurrency test whose runtime varied 4.5× by JDK, and which could stall the build indefinitely.

Where: jdbc/src/test/java/.../JdbcUpdateCallbackTest.java

A concurrency test whose runtime varied 4.5× by JDK, and which could stall the build indefinitely. Two threads run a read-then-update loop against Derby under REPEATABLE_READ, so every contended update produces a genuine lock cycle that Derby has to detect and roll back — the test therefore spends most of its time waiting on Derby's deadlock detector rather than testing anything. Observed: 40 s on JDK 21, 180 s on JDK 25, with a thread dump showing the workers parked in ActiveLock.waitForGrant(). Worse, it called thread.join() with no timeout, so a stuck worker would have hung the build forever, and the workers were non-daemon threads, so a stuck worker would have kept the forked test JVM alive too.

Resolution: Fixed — the workers are daemon threads (a stuck worker can never keep the JVM, and with it the build, alive) and the join has a four-minute timeout with an explicit assertion, so a genuine hang is reported as a test failure instead of a stalled build. The test's logic and assertions are unchanged. Bounding Derby's own derby.locks.waitTimeout was tried as well and reverted: it is not honoured for this database, and passing it as a system property prevented the database from starting at all.

DEP-02 — supply-chain cassandra, mongodb
The Cassandra adapter used com.datastax.cassandra:cassandra-driver-core:3.11.5 and the MongoDB adapter mongo-java-driver:3.1.0 — both years out of date, and the MongoDB one could not use a current server.

Where: cassandra, mongodb/mongo3, mongodb/common

The Cassandra adapter used com.datastax.cassandra:cassandra-driver-core:3.11.5 and the MongoDB adapter mongo-java-driver:3.1.0 — both years out of date, and the MongoDB one could not use a current server. The alias of a FROM item was rendered raw and unescaped in the WHERE / GROUP BY / HAVING / ORDER BY clauses — a SQL injection. Query.clone() cloned the select-clause items with the cloned query, so their SelectItems were re-bound to the cloned FromItems — but it cloned the where-, group-by-, having- and order-by items without it, so their SelectItems kept a detached copy of the FromItem. The JDBC module quotes (and escapes) the alias of a FromItem after cloning the query, so the FROM clause rendered the escaped alias while the WHERE clause rendered the unquoted, unescaped original. A FROM alias of x" , (SELECT 1) AS "y" produced ... FROM t "x"" , (SELECT 1) AS ""y""" WHERE x" , (SELECT 1) AS "y".c = 'v' — the quote character terminates the identifier and (SELECT 1) AS "y" becomes a live subquery. The same inconsistency made the statement syntactically invalid for any alias that needed quoting (WHERE c d.c is three tokens, not a column reference).

Resolution: Fixed — Query.clone() now clones every clause item with the cloned query, so each one is re-bound to the cloned FromItems. FilterItem also clones its child items recursively instead of sharing them with the original query. 3 new core tests (WHERE / GROUP BY+HAVING+ORDER BY / compound filter), mutation-proved: the three fail against the pre-change Query.java (WHERE c.name instead of WHERE "c".name) and pass after it; the other 11 tests in the class pass in both states.

mutation-proved — the new test fails against the pre-fix code

NW-18 S2 adapters sugarcrm (the JAX-WS runtime)
Investigated and closed as _not exploitable_.

Investigated and closed as _not exploitable_. The open item asserted that the inbound SOAP response is parsed by the JAX-WS/JAXB runtime with default (unsafe) settings, and recommended a META-INF/services/com.sun.xml.ws.spi.WSDLParser override. The recommendation was not implementable — that SPI does not exist in JAX-WS RI 2.x (neither 2.3.1 nor the JDK-8 profile's 2.2.10), and it would in any case govern WSDL parsing, not inbound messages. The facts, established by experiment rather than by argument: the inbound response is read by Woodstox 5.1.0 (com.ctc.wstx.stax.WstxInputFactory) through the RI's XMLStreamReaderFactory$Woodstox, whose live configuration is javax.xml.stream.supportDTD=false and IS_SUPPORTING_EXTERNAL_ENTITIES=false — set by the RI itself on the factory instance it creates, so the hardening travels with the RI, not with Woodstox: which StAX implementation is on the classpath does not change the verdict. An entity-bearing SOAP response is therefore rejected (WstxParsingException: Undeclared general entity "xxe"), and the local file it points at never appears in the module's traffic.

Resolution: Closed — no production change was needed. New SugarCrmSoapXxeTest drives the module's real SOAP call path against a local HttpServer that serves the module's own WSDL and a crafted response. It now covers five payload shapes — external general entity, internal general entity, external parameter entity (the classic bypass), external DTD subset and nested entities ("billion laughs") — across four content types (text/xml with and without charset, application/soap+xml, application/xml), plus a benign control that proves the harness really drives the SOAP path and a positive control in which a permissive StAX factory does expand the same payload (proving the payload is armed and that the assertions are not vacuous). Mutation-proved: weakening the parser configuration makes exactly the XXE tests fail with the secret visible in the captured traffic, and reverting makes them pass. The JDK's DOM parser is also loaded — but on the WSDL path, where the RI's XMLEntityResolver and the XML catalog machinery restrict entity resolution; that path was tested too and is protected. Residual risk, recorded: jaxws-rt is a provided dependency, so the consuming application supplies the JAX-WS implementation; the two versions the module pins were verified, a substituted stack was not. The project-level fix for that would be to give jaxws-rt compile scope, which changes the published packaging and is a project decision, not a module-local fix.

mutation-proved — the new test fails against the pre-fix code

Chapter 04

Two findings that were refuted

R-01 was reported as an S1 out-of-scope injection: "IN-list values are rendered into SQL with no escaping." It was refuted on inspection — the investigator had read only the operand instanceof String branch of the rewriter, and missed the branch that handles iterables and arrays, which escapes every string element.

The finding was put back to its originator, who retracted it and added two regression tests that now lock the layering in place.

Why this is in the register at all

A register that only lists what was fixed cannot show that the refutations were checked. Recording them is what distinguishes an audit from a list of complaints — and here, acting on one of them would have introduced a regression into every query with an apostrophe in it. No core change should be routed for R-01.

Chapter 05

The build

The project did not build at all when the audit started. Eight modules were missing from the source tree, and the SugarCRM module had a dependency that could not be resolved: the JAX-WS RI stack transitively requires org.glassfish.jaxb:txw2:2.4.0-b180608.0325, which was only ever published to plain-HTTP repositories that no longer exist — and Maven 3.8+ blocks plain-HTTP outright.

The toolchain was 2020-era. It was replaced, the dependency was pinned to the release that is on Central, and the result is green on two JDKs with the library's Java 8 bytecode floor untouched.

Chapter 06

The supply chain

342 advisories across 461 resolved artifacts; 167 of those advisories affect the 48 coordinates MetaModel pins directly. 23 dependency upgrades were applied and re-verified against OSV before pinning, and the reactor build was re-run afterwards.

The full inventory, the methodology, the scope triage and the rationale for the upgrades that were deferred are in docs/SUPPLY-CHAIN.md. The deferred ones are recorded rather than silently skipped — a dependency that is old is a fact; a dependency that is old and unexplained is a surprise.

Two migrations, not version bumps

The MongoDB adapter moved from mongo-java-driver:3.1.0 to mongodb-driver-sync:4.11.1 and the Cassandra adapter from cassandra-driver-core:3.11.5 to the 4.x OSS driver. Both are API migrations: DB and DBCollection become MongoDatabase and MongoCollection<Document>; Cluster becomes CqlSession. The shared mongodb/common module had to become driver-free, because mongo2 pins the 2.x driver and mongo3 the 4.x one, and a class referenced by common's bytecode may not exist in only one of them. Proven with javap: no com/mongodb or org/bson reference in its bytecode.

Two real bugs, found by the migration

The advised write concern was discarded — withWriteConcern returns a new collection, and the code ignored the return value. And adviceDeleteQuery was never called. Neither was visible before, because the old driver made the same mistake look harmless.

The MongoDB test takes 2.7 s against a live server and 0.07 s when none is configured — which is the proof that the live assertions actually ran.

Chapter 08

What this fork is

Apache MetaModel was retired by the ASF in June 2021 and moved to the Attic in July 2021. The ASF does not release retired projects, so the last upstream commit is the last thing that will ever be published under org.apache.metamodel — including its security holes.

It is

  • The last upstream commit plus the fixes in the register
  • A build that works, on two JDKs, with 1112 tests
  • Green CI on four JDKs, against live datastores
  • Java 8 bytecode — the library's floor, unchanged

It is not

  • An ASF project, or endorsed by the ASF
  • A fork the ASF knows about — yet
  • Published to Maven Central under org.apache.metamodel, which the ASF owns
  • Complete: the sugarcrm module's JAX-WS implementation is supplied by the consuming application, and a substituted stack was not verified
One residual risk, recorded rather than fixed

sugarcrm depends on jaxws-rt with provided scope, so the JAX-WS implementation that actually parses inbound SOAP messages is supplied by the consuming application. The two versions the module pins were verified — and the inbound path was proved not exploitable — but a substituted stack was not. Giving jaxws-rt compile scope would close the gap, and it changes the published packaging of the module, so it is a project decision rather than a module-local fix.

Where it is published

The Maven coordinates of this repository are its own: the ASF owns org.apache.metamodel and Maven Central requires a lowercase artifactId, so the coordinate had to change. It is io.forenxics.metamodel:metamodel-core:5.3.4-forenxics.1. The Java packages are unchanged, which keeps the library a drop-in replacement and means a consumer only has to change the coordinate. The qualifier in the version is what makes it say what it is: a fork of the 5.3.4 line, carrying the security fixes, and not a 5.3.4 that the ASF released.

The repackaging lives on the release/5.3.4-forenxics.1 branch, so that master keeps the upstream lineage and stays legible as a diff against it. Until the fork is published it is built from source. The policy-enforced broker that depends on it installs the fork from source in its own CI, which is why that repository's builds take about eleven minutes.

Appendix

Glossary

The jargon, decoded.

CWE
Common Weakness Enumeration — the MITRE catalogue of software weakness classes. CWE-89 is SQL injection; CWE-611 is XML External Entity processing; CWE-502 is unsafe deserialization.
XXE
XML External Entity processing. A parser that resolves an entity declared with a SYSTEM identifier can be made to read local files and to make outbound requests — a file-disclosure and SSRF primitive in one.
SSRF
Server-Side Request Forgery — making the host issue a request on the attacker's behalf, to somewhere it can reach and the attacker cannot.
SQLi
SQL injection — a value that changes the meaning of the statement rather than being data in it. Identifier injection, the S1 here, is the same idea one level up: the name of a column or table becomes code.
deserialization
Reading an object back out of a byte stream by letting the stream instantiate whatever classes it names. Unrestricted, that is arbitrary code execution; a class allow-list is the fix.
mutation-proved
The audit's term for a test that was run against the pre-fix code and had to fail there. It distinguishes a test that locks in a fix from one that merely passes.
Attic
Where the ASF parks retired projects. An Attic project is frozen: no releases, no security fixes, and — the point here — no 5.3.4 will ever exist.
OSV
Open Source Vulnerabilities — Google's advisory database and its query API, used to re-verify each upgraded coordinate rather than trusting a scanner's verdict.
NVD
National Vulnerability Database. The API needs a key, and the check for that key is a place where a workflow can fail before any job runs.
OWASP dependency-check
The scanner used for the weekly advisory sweep. It fails the build on a threshold rather than on every advisory, because an un-actionable advisory should not stop a release.
Tattletale
The Apache release-assembly plugin that assembles the binary distribution. The root-relative output directories it wants are the intended layout of the ASF release archive, not a defect.
bytecode floor
The oldest Java version the compiled classes will run on. MetaModel's is Java 8, and the fork keeps it: a library that raised its floor would break every consumer that had not yet moved.
Temurin
Eclipse Adoptium's build of OpenJDK — the JDK distribution the fork is verified against, on versions 21.0.12 and 25.0.4.1+1 (LTS).
JEP
JDK Enhancement Proposal — the numbered document through which the JDK changes. JEP 403 (strong encapsulation, Java 9) and JEP 486 (the permanent removal of the SecurityManager, Java 24) are the two that shaped this audit.
JAX-WS / RI
The SOAP web-services stack and its reference implementation. Which parser it uses is decided at runtime, which is why the inbound-SOAP question could only be settled by experiment.
Woodstox
The StAX implementation the JAX-WS RI uses to read messages. Its live configuration here disables DTD support and external entities — set by the RI on the factory it creates, so the hardening travels with the RI.
